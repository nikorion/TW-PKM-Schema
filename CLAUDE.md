# TW-PKM-Schema — contexte projet pour Claude

> **Avant toute tâche sur ce plugin, consulter d'abord le `CLAUDE.md` du workspace** (`../CLAUDE.md`, dont § Suite pkm) et ses `guides/` : outillage de dev commun (pnpm, `dev.cjs`/HMR, Ctrl+C, git push), conventions de nommage/i18n, symlink, test de rendu hors navigateur. Ci-dessous : uniquement le spécifique à TW-PKM-Schema.

## Ce que c'est
Schéma de la suite pkm (`$:/plugins/nikorion/pkm-schema`, créé le 2026-09-28 en sortant champs et vocabulaires de TW-Base-Fields 0.3 (aujourd'hui TW-PKM-Fields), sous le nom `kms-ontology`, renommé le même jour) : une définition par champ (`fields/<champ>.tid`, tag `$:/tags/nikorion/pkm/Field`, ordre = `list` de `tags/Field.tid`), icônes, libellés, descriptions, traductions, et l'**API de lecture `pkm-*`** (`api.tid`) par laquelle passent les autres plugins (TW-PKM-Fields ; TW-Dynamic-Table n'en sait rien, PKM Fields lui fournit les colonnes). Aucun JS, aucune UI hors l'onglet de référence généré.

Docs (règle des trois publics : `../CLAUDE.md` § Conventions) : le readme du plugin porte le sens des champs, les slugs et l'usage en wikitext ; `README.md` le contrat de l'API et l'extension. **Avant d'ajouter ou modifier un champ, une valeur ou une fonction de l'API → lire `README.md`** (§ Source layout, § Extending) — ne pas agir de mémoire.

## Spécificités
- **L'API est le contrat de la suite.** Les consommateurs n'appellent que les `pkm-*`, jamais les tiddlers de définition ni les chaînes. **Avant de renommer/changer une fonction `pkm-*`, un champ de définition lu par l'API, ou d'ajouter un `kind` → répercuter dans les consommateurs, même tâche** : `../TW-PKM-Fields/src/pkm-fields/macros/edit-fields.tid` (+ `readme/controls.tid`) et `dyntable/` (cellules de tableau : `procedures.tid`, `body/<kind>.tid` dont les `nk-dyntable-column-filter` lisent `kind` directement, `column-label.tid`, `row-tones.tid`).
- **Liste des champs = `pkm-all-fields()`, pas `pkm-fields`** (renommée 2026-09-28) : `pkm-fields` est le nom court du plugin éditeur, ne pas les rendre homonymes.
- **Nature d'un champ = `kind`, pas `type`** : `type` est le type de contenu TW du tiddler de définition.
- **Aucune UI de config des vocabulaires, volontairement** : une valeur ajoutée depuis l'interface ne pourrait pas emporter ses traductions. Ne pas en proposer.
- **Seul le slug est stocké** ; icônes/libellés résolus au rendu (langue → en-GB → slug). Ne jamais les faire entrer dans une valeur.
- **Valeur vide (`blank-value`)** : `maturity` (stub), `lifecycle` (active), `status` (none) — **est** le champ vide, jamais stockée ; les consommateurs la montrent tant que le champ est vide et suppriment le champ quand on la choisit. Filtrer avec `[!has[maturity]]`, pas `[maturity[stub]]`. Ne pas réintroduire de valeur par défaut stockée ni de valeur « active » écrite.
- **`applies-filter`** (évalué avec `currentTiddler`) : où un champ a un sens. Filtre négatif écrit `[<currentTiddler>!role[log]…]`, **pas** `get[role]!match[…]` : sans rôle, `get[role]` ne renvoie rien et le champ serait exclu à tort. `status` : `task`/`tasklist`/`routine` ou aucun rôle — **même filtre sur `priority` et `due`, à tenir en phase** entre eux, avec leurs `Field/<champ>/Applies` (ici) et `Fields/status/Stale/Hint` (TW-PKM-Fields). `pkm-field-applies-filter` renvoie la **chaîne** du filtre (vide = partout) : une `\function` ne peut pas l'évaluer elle-même (`:map` relie `currentTiddler` à la chaîne), l'appelant fait `$let` + `[subfilter<…>]`.
- **Tons** (`tone-<ton>: <valeurs>` sur une définition, lus par `pkm-vocab-tone`/`pkm-tones`) : sens d'une valeur (`success` = fait, `muted` = écarté), jamais un style — le consommateur choisit le rendu (PKM Fields : classe de ligne `nk-dyntable-row-<ton>` de Dynamic Table). `pkm-tones` ignore un champ qui ne s'applique pas au tiddler (une référence restée `done` n'est pas verte).
- **`pkm-applies-to` = seul moyen d'évaluer un `applies-filter` dans une `\function`** : la chaîne passe par une fonction sans paramètre lue comme variable (`<pkm-applies-to--filter>`, qui voit le `field` de l'appelant) et `:filter` rend `currentTiddler` = le tiddler. `:map:flat` pousse `""` quand son filtre ne rend rien → toujours finir par `+[!is[blank]]` (vécu `pkm-tones`).
- **Slugs de `priority` = chiffres `2 1 0`** (haute → basse), choix de l'utilisateur 2026-09-28 : le tri sur le champ (texte ou nombre) suit l'urgence. D'où **pas de `blank-value`** : une valeur normale vide trierait à part de `1`. Ne pas revenir à des mots.
- **`needs`, `deviation` sont des listes** (`kind: vocab-list`) : `[contains:needs[verify]]`, jamais `[needs[verify]]`. `epistemology` (critère ouvert) / `regime` (fermé ou privé) / `deviation` (ouvert contourné) = une seule grille (readme § Epistemology) : les tenir en phase. `epistemology` et `regime` à valeur unique (choix utilisateur 2026-09-28 : un savoir = un critère de validation ; transversal ≠ cumulable) ; `deviation` en liste (contrefaçons cumulables).
- **`lifecycle` indépendant de `maturity`** (une note `stable` peut devenir `obsolete`).
- **Groupes de `role`** : purement visuels (`groups`, `group-<slug>`) ; une valeur hors groupe (`hub`, `project`, `tool`) passe avant le 1er intitulé. **Ajouter un rôle = aussi sa clé `Vocab/role/<slug>/Plural`** dans chaque langue (phrase du cadre rouge de l'éditeur).
- **Cascades de libellé dupliquées dans chaque fonction, volontairement** : une `\function` appelée en opérateur direct ne lie pas son opérande (TW 5.4), donc pas de helper partagé.
- **`pkm-pill` : `+[trim[]]` obligatoire sur la couleur de repli** — le texte de `colours/<champ>.tid` finit par un saut de ligne ; non trimé, `contrastcolour` retombe sur `tag-background` et rend un texte sombre sur fond foncé, sans erreur (vécu 2026-09-26). Emplacement `pkm-pill-after` (`$slot`) : son contenu voit les variables de la procédure (`foregroundColor`). **Avant une montée de version TW → lire `README.md` § On a TiddlyWiki upgrade** (copie de `tag-body-inner` à resynchroniser).
- **`$:/config/SyncFilter` du wiki de dev** exclut `$:/plugins/nikorion/pkm-schema/`, `$:/config/nikorion/pkm-schema/` et `$:/tags/nikorion/pkm/Field` (shadows hors du namespace du plugin) : sinon un push HMR les écrit en vrais tiddlers sous `wiki/tiddlers/system/`, copies figées qui masquent ensuite le plugin.
- **Ne jamais conseiller un rechargement d'onglet pour voir une modif** (il annule le HMR). Pour voir l'effet sur l'éditeur et les tableaux : le wiki d'intégration `../PKM` (`pnpm dev`), qui surveille les sources de toute la suite.
