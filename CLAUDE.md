# TW-KMS-Ontology — contexte projet pour Claude

> **Avant toute tâche sur ce plugin, consulter d'abord le `CLAUDE.md` du workspace** (`../CLAUDE.md`, dont § Suite kms) et ses `guides/` : outillage de dev commun (pnpm, `dev.cjs`/HMR, Ctrl+C, git push), conventions de nommage/i18n, symlink, test de rendu hors navigateur. Ci-dessous : uniquement le spécifique à TW-KMS-Ontology.

## Ce que c'est
Ontologie de la suite kms (`$:/plugins/nikorion/kms-ontology`, créée le 2026-09-28 en sortant champs et vocabulaires de TW-Base-Fields 0.3) : une définition par champ (`fields/<champ>.tid`, tag `$:/tags/nikorion/kms/Field`, ordre = `list` de `tags/Field.tid`), icônes, libellés, descriptions, traductions, et l'**API de lecture `kms-*`** (`api.tid`) par laquelle passent les autres plugins (TW-Base-Fields, TW-Dynamic-Table). Aucun JS, aucune UI hors l'onglet de référence généré.

Docs (règle des trois publics : `../CLAUDE.md` § Conventions) : le readme du plugin porte le sens des champs, les slugs et l'usage en wikitext ; `README.md` le contrat de l'API et l'extension. **Avant d'ajouter ou modifier un champ, une valeur ou une fonction de l'API → lire `README.md`** (§ Source layout, § Extending) — ne pas agir de mémoire.

## Spécificités
- **L'API est le contrat de la suite.** Les consommateurs n'appellent que les `kms-*`, jamais les tiddlers de définition ni les chaînes. **Avant de renommer/changer une fonction `kms-*`, un champ de définition lu par l'API, ou d'ajouter un `kind` → répercuter dans les consommateurs, même tâche** : `../TW-Base-Fields/src/base-fields/macros/edit-fields.tid` (+ `readme/controls.tid`), `../TW-Dynamic-Table/src/dyntable/procedures/dt-kms.tid` et `templates/body/kms-*.tid` (dont leurs `tbl-column-filter`, qui lisent `kind` directement).
- **Nature d'un champ = `kind`, pas `type`** : `type` est le type de contenu TW du tiddler de définition.
- **Aucune UI de config des vocabulaires, volontairement** : une valeur ajoutée depuis l'interface ne pourrait pas emporter ses traductions. Ne pas en proposer.
- **Seul le slug est stocké** ; icônes/libellés résolus au rendu (langue → en-GB → slug). Ne jamais les faire entrer dans une valeur.
- **Valeur vide (`blank-value`)** : `maturity` (stub), `lifecycle` (active), `status` (none) — **est** le champ vide, jamais stockée ; les consommateurs la montrent tant que le champ est vide et suppriment le champ quand on la choisit. Filtrer avec `[!has[maturity]]`, pas `[maturity[stub]]`. Ne pas réintroduire de valeur par défaut stockée ni de valeur « active » écrite.
- **`applies-filter`** (évalué avec `currentTiddler`) : où un champ a un sens. Filtre négatif écrit `[<currentTiddler>!role[log]…]`, **pas** `get[role]!match[…]` : sans rôle, `get[role]` ne renvoie rien et le champ serait exclu à tort. `status` : `task`/`tasklist`/`routine` ou aucun rôle — **à tenir en phase** avec `Field/status/Applies` (ici) et `Fields/status/Stale/Hint` (TW-Base-Fields). `kms-field-applies-filter` renvoie la **chaîne** du filtre (vide = partout) : une `\function` ne peut pas l'évaluer elle-même (`:map` relie `currentTiddler` à la chaîne), l'appelant fait `$let` + `[subfilter<…>]`.
- **`needs` est une liste** (`kind: vocab-list`) : `[contains:needs[verify]]`, jamais `[needs[verify]]`.
- **`lifecycle` indépendant de `maturity`** (une note `stable` peut devenir `obsolete`).
- **Groupes de `role`** : purement visuels (`groups`, `group-<slug>`) ; une valeur hors groupe (`hub`, `project`, `tool`) passe avant le 1er intitulé. **Ajouter un rôle = aussi sa clé `Vocab/role/<slug>/Plural`** dans chaque langue (phrase du cadre rouge de l'éditeur).
- **Cascades de libellé dupliquées dans chaque fonction, volontairement** : une `\function` appelée en opérateur direct ne lie pas son opérande (TW 5.4), donc pas de helper partagé.
- **`kms-pill` : `+[trim[]]` obligatoire sur la couleur de repli** — le texte de `colours/<champ>.tid` finit par un saut de ligne ; non trimé, `contrastcolour` retombe sur `tag-background` et rend un texte sombre sur fond foncé, sans erreur (vécu 2026-09-26). Emplacement `kms-pill-after` (`$slot`) : son contenu voit les variables de la procédure (`foregroundColor`). **Avant une montée de version TW → lire `README.md` § On a TiddlyWiki upgrade** (copie de `tag-body-inner` à resynchroniser).
- **`$:/config/SyncFilter` du wiki de dev** exclut `$:/plugins/nikorion/kms-ontology/`, `$:/config/nikorion/kms-ontology/` et `$:/tags/nikorion/kms/Field` (shadows hors du namespace du plugin) : sinon un push HMR les écrit en vrais tiddlers sous `wiki/tiddlers/system/`, copies figées qui masquent ensuite le plugin.
- **Ne jamais conseiller un rechargement d'onglet pour voir une modif** (il annule le HMR). Pour voir l'effet sur l'éditeur et les tableaux : le wiki d'intégration `../KMS` (`pnpm dev`), qui surveille les sources de toute la suite.
